# LLM 에이전트 지식 베이스 설계 전략

방대한 사전 지식 데이터를 API 기반 LLM 에이전트에 연결할 때의 데이터 가공 방식과 호출 구조에 대한 설계 문서.

---

## 1. 기본 원칙

### 1.1 컨텍스트는 예산이다

컨텍스트 윈도우는 "넣을 수 있는 공간"이 아니라 **소모되는 예산**이다. 관련 없는 내용이 들어갈수록 모델의 주의(attention)가 분산되어 정확도가 떨어진다. 넣을 수 있다고 해서 넣으면 안 된다.

핵심 목표는 **"정답에 필요한 최소한의 토큰만 컨텍스트에 올리는 것"**이다.

### 1.2 마크다운은 적절한 포맷이다

- LLM은 마크다운으로 학습된 비중이 압도적으로 높아 헤딩·리스트를 구조 신호로 정확히 해석한다.
- JSON/XML로 변환할 필요 없다. 오히려 토큰만 늘어난다.
- **단, 포맷보다 중요한 것은 "분할 단위"와 "메타데이터"다.** 수천 줄짜리 단일 md 파일은 포맷과 무관하게 실패한다.

### 1.3 검색보다 "지도"가 먼저다

에이전트는 무엇이 존재하는지 모르면 검색 질의를 만들 수 없다. 전체 문서 목록(인덱스)을 항상 보유하게 하는 것이 임베딩 품질 개선보다 효과가 크다.

## 2. 3계층 구조

| 계층 | 내용 | 로드 방식 | 토큰 예산 |
|---|---|---|---|
| **계층 0** | 핵심 규칙, 용어집, 데이터 스키마 | 시스템 프롬프트 고정 | 2,000 ~ 4,000 |
| **계층 1** | 전체 문서 인덱스 (지도) | 시스템 프롬프트 고정 | 1,000 ~ 4,000 |
| **계층 2** | 실제 문서 본문 | 툴 호출 (온디맨드) | 필요 시에만 |

### 2.1 계층 0 — 항상 로드

**들어가야 할 것**

- 도메인 용어 정의 (약어, 내부 명칭, 동의어)
- 절대 규칙 / 제약 조건 (에이전트가 어겨선 안 되는 것)
- 핵심 데이터 스키마, 상태값 enum
- 자주 쓰이는 상수, 기준값

**들어가면 안 되는 것**

- 예시가 많은 긴 설명 → 계층 2로
- 자주 바뀌는 값 (타임스탬프, 세션 정보) → 프롬프트 캐시가 깨진다
- "혹시 필요할까 봐" 넣는 내용

> **판단 기준:** "이 정보 없이 답하면 위험한 답이 나오는가?" → Yes면 계층 0, No면 계층 2.

### 2.2 계층 1 — 인덱스

문서 하나당 한 줄. `id`, `제목`, `한 줄 요약`, `태그`.

```markdown
## 결제 (payment)
- `payment-flow` — 결제 요청부터 승인까지의 전체 흐름 · [payment, core]
- `payment-refund-policy` — 환불 조건, 부분 환불 계산식, 예외 케이스 · [payment, policy]
- `payment-error-codes` — 게이트웨이 오류 코드 대응표 · [payment, ops]

## 사용자 (user)
- `user-tier-rules` — 등급 산정 기준과 등급별 혜택 · [user, policy]
```

- 문서 200개 기준 약 3,000~4,000 토큰. 충분히 감당 가능한 비용이다.
- **frontmatter에서 자동 생성하는 스크립트를 반드시 만들 것.** 수동 관리하면 반드시 어긋난다.

### 2.3 계층 2 — 온디맨드 문서

툴 호출로만 접근. 상세 규격은 4장 참조.

## 3. 데이터 가공 규칙

### 3.1 분할 단위

| 항목 | 기준 |
|---|---|
| 파일 하나 | 주제 하나 |
| 목표 크기 | 500 ~ 2,000 토큰 |
| 분할 기준 | 기존 md의 H2 단위 |
| 최대 허용 | 4,000 토큰 (초과 시 재분할) |

너무 잘게 쪼개면 문맥이 끊기고, 너무 크면 불필요한 토큰이 함께 실린다. "이 문서 하나를 통째로 읽어도 아깝지 않은 크기"가 기준.

### 3.2 Frontmatter 템플릿

모든 문서 최상단에 다음을 부착한다.

```yaml
---
id: payment-refund-policy          # 고유 ID (파일명과 일치)
title: 환불 정책
summary: 결제 취소 조건, 부분 환불 계산식, 예외 케이스 3종
tags: [payment, policy]
keywords: [환불, 취소, 부분환불, refund, 반품]   # 검색 재현율용 동의어
related: [payment-flow, user-tier-rules]
priority: normal                    # critical | normal | reference
updated: 2026-07-12
---
```

- `summary` — 인덱스와 검색 결과에 그대로 노출된다. **에이전트가 이 한 줄만 보고 "열지 말지" 판단할 수 있게** 작성한다.
- `keywords` — 사용자가 쓸 법한 동의어·영문·오탈자 변형. 키워드 검색 재현율을 크게 올린다.
- `priority: critical` — 계층 0으로 승격시킬 후보 표시.

### 3.3 자기완결성 (가장 중요)

검색으로 문서가 단독 반환되면 앞뒤 문맥이 사라진다. 따라서:

**제거할 표현**

- "위에서 설명한 대로", "앞 절 참조", "이 경우"
- 지시대명사로만 지칭된 주어 ("그것은 3일 이내에...")
- 문서 밖 문맥에 의존하는 조건절

**치환 예시**

```markdown
<!-- 나쁨 -->
이 경우 위 정책에 따라 처리한다.

<!-- 좋음 -->
결제 후 7일이 지난 건은 `payment-refund-policy`의 부분 환불 규칙에 따라 처리한다.
```

### 3.4 헤딩과 문체

- 헤딩에 검색될 단어를 심는다. `## 개요` (X) → `## 환불 요청 처리 절차` (O)
- 표와 리스트를 적극 활용한다. LLM은 산문보다 표에서 정확히 값을 추출한다.
- 각 문서의 첫 문단은 그 문서 전체를 요약하는 리드 문장으로 시작한다.

### 3.5 디렉터리 구조

```
knowledge/
├── INDEX.md              # 자동 생성 (계층 1)
├── core/                 # 계층 0 원본
│   ├── glossary.md
│   ├── rules.md
│   └── schema.md
├── docs/                 # 계층 2
│   ├── payment/
│   │   ├── payment-flow.md
│   │   └── payment-refund-policy.md
│   └── user/
│       └── user-tier-rules.md
└── build/
    ├── build_index.py    # frontmatter → INDEX.md
    └── validate.py       # 3.6 검증 스크립트
```

### 3.6 빌드 시 검증 항목

CI에 넣어 자동 검사한다.

- [ ] 모든 문서에 frontmatter 존재, 필수 필드 누락 없음
- [ ] `id` 중복 없음, 파일명과 일치
- [ ] `related`가 가리키는 id가 실제로 존재 (끊어진 링크 검출)
- [ ] 문서 토큰 수가 상한 초과하지 않음
- [ ] `summary`가 비어 있거나 제목을 그대로 복사한 경우 경고
- [ ] 계층 0 총 토큰 수가 예산 내인지 확인

## 4. 호출 구조

### 4.1 툴을 2단계로 분리한다

**가장 흔한 실패:** 검색 툴이 본문 전체를 반환. 한 번의 검색으로 문서 5개가 통째로 들어오면 컨텍스트가 즉시 오염된다.

```
search_docs(query, tags?, top_k=5)
  → [{ id, title, summary, matched_snippet }]     # 본문 없음, ~300 토큰

read_doc(id, section?)
  → 문서 전문 (또는 지정 섹션만)
```

에이전트가 요약 목록을 보고 판단한 뒤 **1~2개만** 여는 흐름. 이 분리 하나만으로 컨텍스트 효율이 크게 개선된다.

### 4.2 툴 정의 예시

```json
{
  "name": "search_docs",
  "description": "지식 베이스에서 관련 문서를 검색한다. 요약만 반환하므로, 실제 내용이 필요하면 반환된 id로 read_doc을 호출해야 한다.",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": {
        "type": "string",
        "description": "검색어. 사용자 질문을 그대로 넣지 말고 핵심 명사 2~5개로 압축할 것."
      },
      "tags": {
        "type": "array",
        "items": { "type": "string" },
        "description": "선택. 특정 카테고리로 범위를 좁힐 때 사용."
      },
      "top_k": { "type": "integer", "default": 5 }
    },
    "required": ["query"]
  }
}
```

```json
{
  "name": "read_doc",
  "description": "지정한 id의 문서 전문을 반환한다. INDEX 또는 search_docs 결과에 있는 id만 사용 가능하다.",
  "input_schema": {
    "type": "object",
    "properties": {
      "id": { "type": "string" },
      "section": {
        "type": "string",
        "description": "선택. 특정 H2 섹션 제목을 지정하면 해당 부분만 반환."
      }
    },
    "required": ["id"]
  }
}
```

> **툴 description은 프롬프트다.** 에이전트가 오용하기 쉬운 지점을 여기에 미리 적어 두는 것이 시스템 프롬프트에 적는 것보다 효과적이다.

### 4.3 시스템 프롬프트 배치 순서

```
1. 역할 정의
2. [계층 0] 용어집 · 규칙 · 스키마
3. [계층 1] 문서 인덱스
4. 검색 사용 지침
   ← 캐시 브레이크포인트
5. (동적) 사용자 컨텍스트
```

고정 콘텐츠를 앞에, 가변 콘텐츠를 뒤에 두어야 프롬프트 캐시가 유지된다.

### 4.4 검색 사용 지침 (프롬프트에 명시)

```markdown
## 지식 참조 규칙

- 인덱스에 있는 주제에 대한 질문은 반드시 문서를 확인한 뒤 답한다. 기억에 의존해 추측하지 않는다.
- 인덱스만 보고 답할 수 있는 질문(어떤 문서가 있는지 등)은 검색하지 않는다.
- search_docs 결과의 summary를 보고 관련 없는 문서는 열지 않는다. 보통 1~2개면 충분하다.
- 검색 결과가 비었으면 다른 표현으로 1회 재시도하고, 그래도 없으면 "해당 정보가 지식 베이스에 없다"고 답한다. 지어내지 않는다.
- 답변에는 근거 문서 id를 표기한다.
```

## 5. 검색 엔진 선택

| 규모 | 방식 | 비고 |
|---|---|---|
| 문서 ~수백 개 / 총 수십만 토큰 이하 | **파일 탐색형** (`list_files` + `grep` + `read_doc`) | 임베딩 인프라 불필요. 인덱스가 잘 되어 있으면 벡터보다 정확한 경우가 많다. |
| 그 이상 또는 질의 표현이 다양함 | **하이브리드** (BM25 + 임베딩, 리랭킹) | 태그 사전 필터링 병행 |

**권장 순서:** 파일 탐색형으로 먼저 구축 → 검색 실패 케이스를 로그로 수집 → 실제로 의미 검색이 필요한 게 확인되면 벡터를 추가.

임베딩부터 시작하면 인프라 복잡도(청킹 전략, 임베딩 모델 선택, 벡터 DB 운영, 재색인 파이프라인)를 먼저 떠안게 되는데, 대부분의 프로젝트에서는 그 비용이 회수되지 않는다.

### 5.1 하이브리드로 갈 경우 청킹

- **문서를 통째로 임베딩하지 말 것.** H2 섹션 단위로 임베딩하되, 각 청크 앞에 `문서 제목 > 섹션 제목` 경로를 붙여 문맥을 보존한다.
- 검색은 청크 단위로 하되, **반환은 문서 id 단위**로 집계한다. (계층 2 툴 구조 유지)

## 6. 비용 최적화

### 6.1 프롬프트 캐싱

계층 0 + 계층 1은 매 호출마다 동일하므로 캐싱 대상이다.

- 시스템 프롬프트 맨 앞에 고정 콘텐츠를 두고 캐시 브레이크포인트 설정
- **캐시를 깨는 요소를 계층 0에 넣지 말 것**: 현재 시각, 세션 ID, 사용자별 정보
- 문서를 수정하면 캐시가 무효화되므로, 배포 단위로 묶어서 갱신

### 6.2 검색 결과 크기 제한

- `search_docs` 반환 총량에 상한을 건다 (예: 1,500 토큰)
- `matched_snippet`은 앞뒤 1~2문장으로 제한
- 긴 문서는 `section` 파라미터로 부분 조회를 유도

## 7. 안티패턴

| 안티패턴 | 왜 문제인가 | 대안 |
|---|---|---|
| 전체 지식을 컨텍스트에 투입 | 주의 분산으로 정확도 하락, 비용 폭증 | 3계층 분리 |
| 검색이 본문 전체를 반환 | 한 번의 검색으로 컨텍스트 오염 | search / read 2단계 |
| 계층 0이 계속 비대해짐 | 캐시 효율 저하, 핵심 규칙이 묻힘 | 예산 상한을 강제하고 초과 시 계층 2로 강등 |
| 인덱스 없이 벡터 검색만 | 에이전트가 무엇을 찾을지 모름 | 인덱스를 항상 로드 |
| 문서 간 상호 참조가 암묵적 | 청크 단독 반환 시 의미 붕괴 | 자기완결성 원칙 + 명시적 id 참조 |
| 인덱스 수동 관리 | 문서와 반드시 어긋남 | frontmatter에서 자동 생성 |
| 청크를 너무 잘게 분할 | 문맥 손실, 검색 결과 파편화 | 500~2,000 토큰 목표 |

## 8. 도입 순서

**1단계 — 재구조화**
기존 md를 H2 단위로 분할하고 frontmatter를 부착한다. 자기완결성 검토를 함께 수행한다. (여기가 전체 작업의 대부분을 차지한다)

**2단계 — 계층 0/1 구성**
용어집·규칙을 분리하고, 인덱스 자동 생성 스크립트를 만든다.

**3단계 — 툴 연결**
`search_docs` / `read_doc`을 파일 탐색 기반으로 구현하고 시스템 프롬프트에 사용 지침을 넣는다.

**4단계 — 평가셋 구축**
실제 질문 30~50개와 각각의 정답 문서 id를 정리한다. 이후 모든 개선의 판단 기준이 된다.

**5단계 — 캐싱 적용 및 계측**
질문당 토큰 사용량, 검색 정확도(정답 문서를 열었는가), 응답 지연을 측정한다.

**6단계 — 필요 시 하이브리드 검색 도입**
4단계 평가셋에서 실패하는 케이스가 의미 검색으로 해결되는지 확인한 뒤에만 진행한다.

**데이터**
